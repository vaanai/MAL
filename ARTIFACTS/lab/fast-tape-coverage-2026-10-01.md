## Read this first

- **This is not the 2.2 sign-off.** The trial started at 16:25:38Z and this was run at 16:33Z, so the window is 6.4 minutes and contains **0 complete UTC hours**. The task asked for at least the first two complete hours after 16:25Z; those are 17:00-18:00Z and 18:00-19:00Z and do not exist yet. Re-run at or after 19:00Z with `python3 -m tools.tape_coverage --start 2026-10-01T17 --end 2026-10-01T19 --json-out <f> --md-out <f>`.
- **The number is 85.828% against the 95% bar: FAIL on this window**, but it is not evidence that the fast tape is incomplete. Oracle's tape is not a clean reference right now. The two tapes disagree in both directions: **48.4% of fast rows in the window are not on Oracle's tape** (reverse coverage 51.617%), and fast recorded 81,430 rows in the window against Oracle's 51,129. Per-minute row counts (timestamps only) at 16:28 and 16:29Z were 19,331 and 18,820 on fast against 11,606 and 11,801 on Oracle.
- Oracle's own tape counters (`/var/lib/mal/sealed/trades/stats-2026-10-01.jsonl`, operational counters, read-only) for the three 10-minute windows ending 16:03:11Z, 16:13:12Z and 16:23:13Z: `reconnects` 12, 11, 12; `lag_p50_s` 5.65, 8.96, 6.60 (`lag_p99_s` 32.7, 19.9, 31.9); `trades_per_min` 11,283, 12,625, 11,137. That is about one reconnect a minute and a multi-second median delay on Oracle's public feed, against the +128 ms lead and 99.98% coverage measured on 2026-09-27 in a calm window. A reconnecting `logsSubscribe` drops notifications, which fits Oracle missing trades the fast host has. This is consistent with the data, not proven: there is no ground truth (no `getBlock` comparison) in this run, and the fast trial has not yet written its own stats file (first one is due about 10 minutes after start).
- **The lag numbers are not a lead measurement.** Matched pairs spread by seconds in both directions (p10 -10.5 s, p90 +6.4 s; half the pairs are more than 5 s apart). That is feed jitter or replay after reconnects on at least one host, far above the NTP offsets (+1 to +20 ms) the task named as the caveat. Do not quote the p50 of -2.2 s as "fast leads by 2 s".
- **Cross-check of the tool.** For the single minute 16:27:00-16:28:00Z (30 s margin) I recomputed coverage with plain Python sets of `(signature, event_index)`, no hashing and no numpy, and got 7,658 Oracle rows, 12,658 fast rows, 86.641% and 54.740% reverse, identical to the tool's output for the same window.
- **Field names.** Rows on both hosts come in two shapes, 18 fields and 27 to 32 fields (the names are in the JSON under `schemas`). On 7,390 matched rows the fast row carries four fields the Oracle row does not: `creator_fee`, `lp_fee`, `pool_quote_amount`, `protocol_fee` (and one more row with `zero_sol`). The inventory note says the field names are identical; that holds for the 18-field rows (36,201 matched rows identical) but not for these full-form rows, so the fast tape code is not the same build as Oracle's. The runner reads those four fields as optional (DEC-015 2.1 inventory), so this is a note for the 2.3 equivalence work, not a finding that anything is broken. Values were not compared.
- Identity here is `(signature, event_index)`: `observe.trade_decode.records_from_logs` numbers every trade in a transaction, so a transaction can hold several. Oracle has 51,129 identities over 50,259 signatures in the window, so about 1.7% more identities than signatures.

### What this does not measure

- Hashing: identities are compared as 8-byte blake2b hashes. A collision would count as a match; expected rate is below 1e-7 at this size.
- Window is bounded by `t_recv_ms` on each host; a trade stamped in a different second near a window edge is matched through a 10.0 s margin on both sides.
- No claim about the runner, its lag, or any book.
