## What the code does at every process start (77bdf7e)
1. main() builds ArenaState(a.tape_dir) with the default warm_min. WARM_MIN_DEFAULT = 365 (arena_state.py line 66), so start_ms = construction time - 365 min. The "~125 min" in the brief matches the out-of-date usage line at arena_state.py line 4, not the constant. Next comes run.resume(): it verifies the chains, rebuilds the books from the decision log, calls engine.recover() (open positions come back with restarted=True), writes resume_reopen rows and writes the start row. Then run.run(start) with start = max(clock_start_ms, now).
2. The constructor reads no rows. The first step(T) calls poll_to(T), which is state.poll(until_ms=T-1) with max_rows=None. That call drains the whole warm-up before exits(T) runs: every row from start_ms to T-1, each one through the apply hook, which also feeds the engine and _on_row.
3. So no exit is ever evaluated on a partial state. The first exit check sees a complete state as of T-1, but by then the wall clock has moved on by the drain time (~130 s here). The next ticks run without sleeping (lag <= 0) until T catches up with the wall clock. Every decision in that window uses a state that is complete up to T-1 but behind the wall clock by the lag still left. That is what the 14:35-14:37 tick_timing rows show.
4. The first start and every restart run the same code path. Nothing tells them apart, except that the first start has no open positions.
5. arena_paper.recover() sets restarted=True. sell() then books such a position as an excluded row with reason engine_restart, however late the sell is (arena_paper.py lines 1105-1108 and 1154-1156). A recovered position that is never sold is a restart orphan, and the read is NOT_DECIDABLE. An excluded share above 5% of a book is also NOT_DECIDABLE.
6. If the job starts before its clock, run() sleeps first and polls at the first tick. So the drain always lands in the first minutes of the clock, and since start_ms is fixed when the job is built, an earlier build makes the drain longer.

## (b) A mid-window restart in run mode
- Exits on a partial state: no, by points 2 and 3. Nothing to fix there.
- Recovered positions: a delayed code exit (drain plus catch-up, on top of the outage) cannot move a scored number, because each one is booked as excluded (engine_restart) whenever its sell fires. It counts toward the excluded share. This is acceptable as a disclosed restart-class event (the restart is recorded in LAB_STATE, per hv4-runner-job.sh lines 5-7).
- That exclusion does NOT cover new decisions made inside the catch-up window: scans, LLM entries, re-checks, and code exits of positions opened inside the window. These are scored, and they are made on a state that is behind by up to the drain time. This happens after any restart AND at the T0 start itself (point 6). The T0 start is not a safety stop and has no restart to disclose.

Ruling (b): recovered positions do not block registration. For scored decisions inside a catch-up window, T0 may register without a runner change ONLY if C1-C3 hold. If C1 fails, the runner must be changed before registration.
- C1 (blocks registration if it fails): show in writing on the registration PR, from arena_paper at 77bdf7e, that a buy or sell called during catch-up lands at or after the slot of the wall-clock call instant, NOT at the slot of the last feed row the engine has seen through the lagging apply hook. The engine's call clock is now_fn() at the call (line 1031). The docstrings at lines 23, 605-606 and 1282 say a stale stamp is priced at the write instant and decision_slot can only push the landing later. I could not finish this read within the 6-call budget, so it is UNVERIFIED. If the landing comes from the lagging feed row, catch-up fills are priced up to ~130 s before a live order could land. Those are not fills a live bot could get, and the runner must change.
- C2: the read lists every catch-up window (the T0 start and each restart, by the rule in (a)). Per book, it reports the trades whose entry or exit decision falls inside a window. Their fills are kept as booked (the declaration says a trade is kept at the fill it actually got), and the read states its verdict both with and without them.
- C3: start the T0 job only as early as needed before 2026-10-21T00:00Z. Report the T0 catch-up the same way as a restart's.
Preferred, but not required if C1 holds: pre-warm in main(). After resume() and before the first tick, drain the state up to the wall clock, then start ticking at the wall clock after the drain. That cuts catch-up to about zero for T0 and for restarts. It is a runner change, so it needs the md5 decision-equivalence replay proof, a new sha and a new 24 h stub. Under SHAKEDOWN-CHECKS-2 that stub must start by 2026-10-20T00:00Z to keep T0 = 2026-10-21T00:00Z; otherwise T0 moves.
Run-mode caveat: the stub cannot measure catch-up with Haiku calls inside the scans. A scan inside catch-up adds its LLM wall time to the drain. Measure and report the catch-up time at T0 and after each restart in the forward run; do not assume it equals the stub's ~3 min.
