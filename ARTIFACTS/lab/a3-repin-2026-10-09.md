## 4. The pump Global gained a byte: no length or sha check can halt on it

I checked the monitor code, and nothing needs to change.
- `pump_global` is in `INFO_ACCOUNTS`, not `PINNED_ACCOUNTS` (`tools/pump_structure_monitor.py:90-96`). The record shows `"pinned": false`, `len` 1,088, sha256 `32729edb5b0d…`.
- `compare_pins` skips every account whose record is not pinned (`:1322`). `build_pins` writes only pinned accounts (`:1695`). So the pins hold no length or sha for it, and a 1,087 to 1,088 byte change cannot trip `pins_changed`.
- The only length guard on a Global is `GLOBAL_CONFIG_LEN = 949`. That is the **PumpSwap GlobalConfig**, which did not change (949 bytes, same sha256).
- A new test, `test_pump_global_growing_by_one_byte_is_not_a_pins_change_or_a_halt`, builds the 1,088-byte Global from the recorded 1,087-byte one plus a trailing `\x01` (a constructed input, labelled as such) and checks that no pin and no halt flag moves.

**What did need a change: test fixtures.** `tools/fixtures/pump_structure_monitor/programdata.json` held the 10-08 slice with the old deploy slots, and 16 tests pair it with the committed pins. I re-recorded it from public RPC with the monitor's own call (context slot 454801133; the three slots equal the new pins). The monitor code is untouched.

Two things to know:
- `program_changed` is a **WARN** (`WATCH_RULES`), not a halt. A same-slot byte change would warn but not halt. A new deploy slot still halts, through `pins_changed`.
- `EXP/EXP-022-cap-pick-part1-prereg.md:356` cites the BOOST pins at `tools/pump_structure_pins.json:41-42`. The six added hash lines move them to `:47-48`. The values are the same. I did not edit the pre-registration.
